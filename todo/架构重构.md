### 核心问题

1. **grid_window.rs 是一个巨型文件**：混合了 Win32 FFI 类型定义、D2D 渲染、窗口过程、Shell 右键菜单、Tooltip、命中测试、布局计算、图标绘制 — 8+ 种职责堆在一起
2. **平台抽象层太薄**：`DesktopManagerTrait` 只有 3 个方法，渲染/窗口/图标提取全部硬编码 Windows API，macOS 完全无法复用
3. **配置系统碎片化**：layout.json、categories.yaml、AppSettings 各管各的，没有统一配置
4. **无插件机制**：所有功能硬编码，无法灵活扩展
5. **全局状态散落**：`GRID_WINDOWS`、`CLASS_REGISTERED`、`ICON_HIDER` 等全局 Mutex 分散在各文件
6. **settings.rs 几乎是空的**：没有 AI 配置、热键配置、样式详细配置

## 三、核心架构设计

### 3.1 AppContext — 中心上下文对象

所有模块通过 `AppContext` 共享状态和配置，替代散落的全局变量：

```rust
// src/context.rs
pub struct AppContext {
    /// 统一配置（从 JSON 加载，可导出/导入）
    pub config: AppConfig,
    /// 平台服务（Windows/macOS 各提供一套实现）
    pub platform: Box<dyn PlatformService>,
    /// 分类框管理器
    pub box_manager: BoxManager,
    /// 分类器
    pub classifier: AppClassifier,
    /// 插件注册表
    pub plugins: PluginRegistry,
    /// 运行时状态
    pub state: AppState,
}

pub struct AppState {
    pub icons_hidden: bool,
    pub panel_visible: bool,
    pub status_message: String,
}

impl AppContext {
    pub fn new(config: AppConfig) -> anyhow::Result<Self> { ... }
    pub fn reload_config(&mut self) -> anyhow::Result<()> { ... }
    pub fn export_config(&self, path: &Path) -> anyhow::Result<()> { ... }
    pub fn import_config(&mut self, path: &Path) -> anyhow::Result<()> { ... }
}
```

### 3.2 平台抽象 Trait

```rust
// src/platform/mod.rs

/// 平台服务总接口 — 每个平台实现一套
pub trait PlatformService: Send {
    /// 桌面图标管理
    fn desktop_manager(&self) -> &dyn DesktopManagerTrait;
    /// 渲染后端
    fn render_backend(&self) -> &dyn RenderBackend;
    /// 窗口管理
    fn window_backend(&self) -> &dyn WindowBackend;
    /// 图标提取
    fn icon_service(&self) -> &dyn IconService;
    /// 图标隐藏/恢复
    fn icon_hider(&self) -> &dyn IconHider;
    /// 系统托盘
    fn tray_service(&self) -> &dyn TrayService;
    /// 屏幕信息
    fn screen_info(&self) -> ScreenInfo;
}

/// 渲染后端 — 负责将分类框内容绘制到屏幕上
pub trait RenderBackend: Send {
    /// 渲染一个分类框到其窗口
    fn render_box(&self, ctx: &RenderContext) -> anyhow::Result<()>;
    /// 初始化设备资源
    fn init(&mut self) -> anyhow::Result<()>;
    /// 释放设备资源
    fn cleanup(&mut self);
}

/// 窗口后端 — 负责窗口的创建、销毁、生命周期
pub trait WindowBackend: Send {
    /// 创建一个分类框窗口
    fn create_box_window(&self, params: &BoxWindowParams) -> anyhow::Result<WindowHandle>;
    /// 销毁窗口
    fn destroy_window(&self, handle: WindowHandle) -> anyhow::Result<()>;
    /// 销毁所有窗口
    fn destroy_all(&self);
    /// 获取窗口数量
    fn window_count(&self) -> usize;
}

/// 图标服务
pub trait IconService: Send {
    fn extract_icon(&self, file_path: &str) -> Option<RawIconHandle>;
    fn destroy_icon(&self, handle: RawIconHandle);
}

/// 图标隐藏器
pub trait IconHider: Send {
    fn hide_native_icons(&mut self) -> anyhow::Result<()>;
    fn restore_native_icons(&mut self) -> anyhow::Result<()>;
    fn is_hidden(&self) -> bool;
}

/// 系统托盘
pub trait TrayService: Send {
    fn create_tray_icon(&mut self) -> anyhow::Result<()>;
    fn remove_tray_icon(&mut self);
    fn show_context_menu(&self, items: &[TrayMenuItem]);
}
```

### 3.4 Plugin 系统

```rust
// src/plugin/mod.rs

/// 插件 trait — 所有功能模块都作为插件注册
pub trait Plugin: Send {
    /// 插件唯一 ID
    fn id(&self) -> &str;
    /// 插件名称
    fn name(&self) -> &str;
    /// 初始化（在 AppContext 创建后调用）
    fn init(&mut self, ctx: &mut AppContext) -> anyhow::Result<()>;
    /// 插件提供的菜单项（控制面板 & 托盘）
    fn menu_items(&self) -> Vec<PluginMenuItem>;
    /// 处理菜单命令
    fn handle_command(&mut self, cmd: &str, ctx: &mut AppContext) -> anyhow::Result<()>;
    /// 清理
    fn cleanup(&mut self, ctx: &mut AppContext);
}

pub struct PluginMenuItem {
    pub id: String,
    pub label: String,
    pub icon: String,
    pub shortcut: Option<String>,
}

pub struct PluginRegistry {
    plugins: Vec<Box<dyn Plugin>>,
}

impl PluginRegistry {
    pub fn register(&mut self, plugin: Box<dyn Plugin>) { ... }
    pub fn init_all(&mut self, ctx: &mut AppContext) { ... }
    pub fn all_menu_items(&self) -> Vec<PluginMenuItem> { ... }
    pub fn dispatch_command(&mut self, cmd: &str, ctx: &mut AppContext) { ... }
    pub fn cleanup_all(&mut self, ctx: &mut AppContext) { ... }
}
```

### 3.6 分类框业务逻辑拆分

```
box_core/ 是平台无关的业务逻辑层：

box_model.rs      → ClassificationBox 数据模型
                    - id, name, items, locked, sort/view/group 状态
                    - 不包含任何渲染/窗口代码

box_manager.rs    → 管理所有分类框的生命周期
                    - create_box(), delete_box(), find_box()
                    - save_layout(), load_layout()
                    - 调用 PlatformService 创建/销毁窗口

sort_engine.rs    → 排序算法
                    - 8种排序维度 × 升降序
                    - sort_items(items, mode, ascending) → Vec<GridFileItem>

view_engine.rs    → 视图模式布局参数
                    - get_view_params(mode) → ViewParams { icon_size, cell_w, cell_h, cols, ... }
                    - 8种视图模式的具体参数计算

group_engine.rs   → 分组逻辑
                    - group_items(items, group_by) → Vec<Group>
                    - 每个 Group 有标题和子项列表

layout_calc.rs    → 网格布局计算
                    - calculate_grid(window_size, view_params, dpi) → GridLayout
                    - hit_test(layout, click_pos) → Option<usize>

interaction.rs    → 交互状态机
                    - BoxInteractionState { selected, hovered, dragging, resizing }
                    - 状态转换方法
```

## 六、依赖关系图

```
main.rs
  ├── context.rs (AppContext)
  │     ├── config/ (AppConfig 统一配置)
  │     ├── platform/ (PlatformService trait + 平台实现)
  │     │     ├── windows/ (D2D渲染 + Win32窗口 + Shell菜单)
  │     │     └── macos/   (CoreGraphics + NSWindow)
  │     ├── box_core/ (分类框业务逻辑 - 平台无关)
  │     │     ├── box_model.rs
  │     │     ├── box_manager.rs → 调用 platform/
  │     │     ├── sort_engine.rs
  │     │     ├── view_engine.rs
  │     │     └── group_engine.rs
  │     ├── classification/ (分类规则 + AI分类)
  │     └── plugin/ (插件注册表)
  ├── ui/ (egui 控制面板)
  │     ├── control_panel.rs → 调用 context
  │     └── settings_panel.rs → 修改 config
  └── utils/ (日志、DPI、字符串)
```

**核心原则**：
- `box_core/` 不直接调用 `platform/` — 通过 trait 对象间接调用
- `classification/` 不依赖 `platform/` — 纯业务逻辑
- `ui/` 只通过 `AppContext` 与后端交互
- `platform/` 各平台实现互不依赖 — 通过 `#[cfg]` 隔离

## 八、风险控制

1. **Phase 0 零风险**：只移动非代码文件，不改任何逻辑
2. **Phase 1 最安全**：纯文件拆分，不改逻辑，每步编译验证
3. **Phase 2-3 中等风险**：引入 trait 层和统一配置，需要确保 Windows 实现完全等价
4. **Phase 4-6 渐进式**：新功能增量添加，旧功能不受影响
5. **全程保持 `cargo build` 通过**：每个 Phase 完成后必须编译通过+手动测试
